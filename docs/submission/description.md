## A. 一言で（約200字）

**高校生から社会人まで、自分の目的（学業・留学・研究・プロジェクト）で応募できる奨学金・助成金を、Web から探して「確かめて」届けるエージェント。** 立場・地域・目的を入れると、AI が民間財団・企業・自治体・大学の制度をインターネットから探し、**各団体の公式ページを読んで、応募できるかをコードで判定**します。募集終了と、確認できないものは分けて出すので、「見つけたつもり」を混ぜません。AI の操作は、許可リスト・上限・人間の承認・監査ログで管理しています。

## B. 詳しい説明

### 1. ユーザー像と課題
- **ユーザー**: 奨学金・助成金を探している個人。**高校生・大学生・大学院生・短大・高専・専門学校生、卒業後（卒業後2年まで応募できる制度もある）の社会人**。目的も、学業・生活費、留学、研究、プロジェクトや活動の一次支援金と幅広い。自分が応募できるものだけを、期限に間に合ううちに知りたい。
- **課題**: 奨学金は、大学の掲示、財団のサイト、自治体の一覧、まとめサイトに散らばっている。生成AIに「全部教えて」と聞いても、次の穴がある。
  1. 検索結果の**上位数件しか読まない**（漏れる）
  2. **古い年度・募集終了**のものを混ぜる
  3. 「自分は対象外」の条件（学年・地域・併給・卒業後・使途）を**取りこぼす**
  4. 「全部」と言えない（**どこまで探したか分からない**）
- 実際に、公式の要項で30件を照合したところ、10月時点で約半数がすでに募集終了だった（10/15 の再実験は29件中14件）。また、素のAIに同じ質問をした回答34件のうち、**12件（約3分の1）は、公式ページで見ると募集終了**だった（10/15、4つの立場。後述の比較実験）。

### 2. 解決策と特徴
**「探す」と「判定する」を分け、判定は AI ではなくコードで行う。**

| 段階 | 内容 |
|---|---|
| ① 発見 | 立場・地域・目的から検索語をコードで作り、Gemini＋Google 検索で6通りを並列に検索して、候補（名前・団体）を集める。年度は固定せず、「いま応募できる（募集中、または次年度採用）」を探す |
| ② 統合 | 別名・重複を1件にし、他大学・他地域・留学生向けなど明らかな対象外を除く |
| ③ 照合 | 候補ごとに**運営団体の公式ページ（PDF含む）**を探して読み、条件を**引用つき**で抜き出す。引用が原文にあるかを**コードで照合**し、作り話は判定に使わない |
| ④ 判定 | 学年・地域・分野・併給・締切・卒業後・使途（目的）を**コードで**判定し、「応募できる」「要確認」「目的が違う」「未確認の候補」「募集終了」に分ける |

- **確認できないものは、隠さず分ける。** 公式ページを読めなかったものは「未確認の候補」、条件の一部が確認できないものは「要確認（何を確認すればよいかを明示）」。確認できない条件を「合っている」とは言わない。
- **目的で絞る。** 留学専用の制度を、学業が目的の人には出さない（「目的が違う」に分け、理由を示す）。
- **上限を決め、超えた分も隠さない。** 検索6回・照合16件・全体で約140秒。超えた分は「未確認の候補」として出す。
- **共有キャッシュ。** 公式ページから抜き出した条件を保存し、再検索は速い（初回は約2分、再検索は約30秒）。判定は利用者ごとにそのつどコードで行う。
- **保存と持ち帰り。** 結果を保存リストに保存し、CSV でダウンロードできる（本人の領域なので承認は不要）。
- **共有リスト（承認つき）。** 自分が見つけた制度を、**他の利用者にも「候補」として見せる**ための登録。他の人にも影響が及ぶので、ここだけは本人が確認ダイアログで許可するまで実行しない（AI は許可できない）。個人の検索結果や保存リストには影響しない。
- **筑波大学の学生には、大学経由の奨学金も併用。** 大学の公開一覧（学内締切つき）を同じ判定にかける。

### 3. 審査基準との対応
**課題の新規性と解決策の有効性**: 生成AI検索の穴を、先行研究の手法（集合拡張、候補ごとの公式ページでの2段構えの照合、確認できないものを混ぜない出し方）で塞ぐ。実験は3つ。
- 集合拡張（10/9・10/15）: 種の4〜5件から、一覧ページ経由で新たに約570〜680件の候補が見つかり、30件を公式要項で照合した。引用は全件が原文と一致した（60／60、81／81）。約半数は10月時点で募集終了。
- **素のAIとの比較（10/15、4つの立場）**: 同じメッセージを渡した素のAIは、34件を挙げ、うち12件（約3分の1）が募集終了だった。本エージェントは、募集終了を分けて出し、募集中の項目には公式ページの引用で確認した締切を付ける。**見つけた「使える」件数は同程度**（本エージェント17件、素のAI 15件。重なりは7件）で、どちらかだけが見つけたものがある。「大幅に多く見つける」とは言えない。
- 実験から直した点: 最初の検索語は「2026年度の募集」と固定していたため、秋には締切済みばかりが出て、素のAIより劣った。検索語を「いま応募できる（募集中・次年度採用）」に直し、劣っていた条件が改善した（大学生: 0件→5件）。

**自律性・エージェントらしさ（可観測性・セキュリティ・信頼できる動作）**
- 状況に応じて動く: 情報不足なら聞き返す（立場・卒業後の年数など）／存在しない都道府県などはガードが止める／混雑・失敗時は安全な文面にフォールバック。検索の進め方（検索語の組み立て、公式ページの選び方、上限の中での優先順位）はコードが決め、AI は読み取りに使う
- 監査ログ: 誰が・いつ・何を・なぜ・結果（許可／停止／実行）を、1操作ごとに Firestore に記録し、画面で見られる
- 人間の承認: 他の人にも影響する操作（共有リストへの追加）は、**本人が許可ダイアログで許可するまで実行しない**。AI は承認の操作を持たず、許可は操作・引数・本人・期限・1回限りに結びつく
- Web ページの内容は命令として扱わない（要項に混ぜた指示で判定が変わらないことを、実際の Gemini でテスト）

**実装品質と拡張性（運用性・費用対効果）**
- 単一エージェント＋ツール3つ（マルチエージェントにしない）。並列化はツールの中のコードで行う
- Cloud Run（最大1インスタンス、ゼロまでスケールダウン）＋ Firestore。専用サービスアカウントに最小権限
- 費用の考え方: 1回の検索は、検索6回＋公式ページの読み取り最大16件（Gemini Flash 系）に上限を固定。会話あたり検索3回・LLM 呼び出し20回の上限、予算アラート。**公式ページから抜き出した条件を共有キャッシュに保存**するので、利用者が増えるほど1人あたりの読み取りが減る。キャッシュの保存期間は環境変数で変えられる

### 4. アーキテクチャ
![アーキテクチャ図](architecture.png)

- 入口は Cloud Run の1サービス。Basic 認証（パスワードは Secret Manager、未設定なら全拒否）の内側に、利用者向けサイト（`/`）、管理・許可・保存 API（`/admin/`）、ADK の API（`/run_sse`）がある
- ADK エージェント（Gemini 3.8 Flash、Vertex AI）に、`before_tool_callback`（許可リスト・引数検証・上限・承認待ち）、`after_tool_callback`（監査ログ）、`on_model_error_callback`（フォールバック）を設定
- ツール: `find_scholarships`（探して判定）、`get_scholarship_detail`（筑波大学の一覧の詳細）、`register_shared_scholarship`（高リスク）
- データは Firestore（監査ログ・承認・キャッシュ・共有リスト・保存リスト）。外部は Vertex AI（Gemini と Google 検索グラウンディング）とインターネット

### 5. セキュリティとガバナンス
| 要件 | 実装 |
|---|---|
| 引数の検証・許可リスト・上限 | ツール実行の直前に検証。許可リスト外のツールは実行しない。検索回数・LLM 呼び出し回数・検索の件数と時間に上限 |
| 人間の承認 | 共有リストへの追加は、承認待ちで止め、本人の許可（確認ダイアログ）だけで実行。AI は承認できない。使い回し・内容のすり替えは拒否 |
| 監査ログ | すべての操作を記録し、画面（操作の記録）と管理画面で閲覧 |
| 権限分離 | エージェント専用のサービスアカウント。Firestore・Vertex AI・秘密1つだけの閲覧権限のみ |
| 安全なフォールバック | 拒否・聞き返し・失敗時は、理由を伝えて止まる。勝手に条件を変えて再試行しない |
| プロンプトインジェクション | ページの内容はデータとして渡し、引用を原文と照合。判定はコード |
| Web 取得の安全 | robots.txt を守る。http(s) のみ。内部アドレス（メタデータサーバー等）は取得しない。転送先も毎回確認 |
| 画面の安全 | Web 由来の文字列を HTML として解釈しない。同一オリジンの書き込みのみ。CSV の式の実行を防ぐ |

### 6. 評価
- 自動テスト 約175件（判定の論理、ガード、承認フロー、Web 検索、取得の安全性、画面の安全性など）。実際の Firestore・Gemini を使うテストを含む
- `adk eval` 7ケース（すべて合格）: 正常系／情報不足での聞き返し／卒業後の人の詳細を聞き返す／指示を無視させる要求を断る／承認待ちで止まる／偽の承認IDを止める／存在しない都道府県をガードが止める
- 比較実験（素のAI 対 本エージェント、4つの立場、各1回）: `docs/experiments/2026-10-15_baseline/`。限界（小さなN、正解の一覧がない、検索語は実験の結果を見て直した）も記載
- 本番での通しの実測（筑波大学・理工学群・3年）: 初回 約2分、再検索 約30秒
- コードレビューを区切りごとに実施（10月9日に20件、10月15日に複数回、指摘を修正）

### 7. 実装済みと拡張予定（正直な範囲）
| 実装済み | 拡張予定 |
|---|---|
| 立場（高校生〜社会人）と目的（学業・留学・研究・活動）の入力、卒業後・使途の判定、目的別の検索語 | 他大学の公開一覧への対応、ログイン方式（現在は共有のテスト用アカウント） |
| Web 全体の検索（6通りの並列検索）、重複の統合、公式ページでの引用つき照合、コード判定 | **検索の出典を使った一覧ページの展開**（実験では効いたが、現在の本番は出典が返らず働いていない。出力形式の指定が原因と分かった） |
| 確認できないものを分けて出す／上限を超えた分も隠さない／募集終了を分ける | 検索語の自動選択（同じ検索を繰り返さず、新しく見つかりそうな言葉から選ぶ）、Chao 推定量による「どこまで探せたか」の推定 |
| 保存・CSV・共有キャッシュ・承認・監査ログ・評価セット | 再現率の数値化（人が数えた正解の一覧との比較） |

### 8. 動かし方（審査員向け）
1. 公開URLを開き、テスト用アカウントでログインする（ID とパスワードは提出フォームに記載）
2. 「入力例を入れてみる」→「奨学金を探す」。初回は約2分（画面に経過時間が出る）
3. 結果の「保存する」→ 右の「保存した一覧」から CSV でダウンロード
4. 続けて「『（奨学金の名前）』を共有リストに追加したい。公式ページは https://… 」と入力すると、**確認ダイアログ**が出る（許可するまで実行されない）
5. 右の「操作の記録」で、AI が何をしたかを確認できる

### 9. 使っている技術
Google Cloud（Cloud Run／Vertex AI／Firestore／Secret Manager／Cloud Build）、ADK（Agent Development Kit）、Gemini 3.8 Flash（Google 検索グラウンディング）、Python（uv）、FastAPI、Material Design 3 の画面。
