# 人間の承認（Human-in-the-loop）：既存のエージェントのやり方（2026-10-13）

目的: F11「高リスク操作で人間の承認を挟む」の対象操作と方式を決める材料。出典は末尾。二次情報（ブログ等）は「要裏付け」と書いた。

## 1. 各社・各フレームワークの方式

| 製品 | 承認の仕組み | 特徴 |
|---|---|---|
| ADK（Google） | `FunctionTool(fn, require_confirmation=True)`。引数で条件分岐もできる。REST では `adk_request_confirmation` の呼び出し ID に `confirmed` を返して再開 | **実験的。`DatabaseSessionService` と `VertexAiSessionService` 非対応**（再起動で状態が消える in-memory 前提）。**誰が承認できるかの認証は仕様にない** |
| LangGraph | ツールの中で `interrupt()` → チェックポイントに保存 → `Command(resume=...)` で再開。承認／編集／却下を選べる | 状態を永続化するので、何日待っても再開できる（非同期の承認） |
| OpenAI Agents SDK | ツールに `needs_approval`（真偽、または呼び出しごとの判定関数）。保留は `result.interruptions` に出て、`approve`/`reject` して再開 | 一時停止するだけで、**人への通知や記録は含まない**（要裏付け） |
| Claude Code | `deny → ask → allow` の順に規則を評価（先に一致した方）。モード（default / acceptEdits / plan / dontAsk など）で既定を切り替え | **強制はモデルではなくアプリ側**。プロンプトの指示では権限は変わらない。読み取りは許可、書き込みは確認、本番デプロイは拒否、が推奨 |

## 2. 共通する設計原則（OWASP LLM06「過剰な権限」ほか）
1. **承認は、影響が大きい・元に戻せない操作だけに絞る。** 何でも聞くと承認疲れ（approval fatigue）で、確認が形だけになる。実際の実装では「読み取りは自動、書き込みは確認、危険なものは拒否」の3段階が多い
2. **強制はコード側。** モデルへの指示では止められない（Claude Code、OWASP とも同じ）
3. **承認は、ツール名・引数・期限に結びつける。** 引数が変わったら無効（実務ガイド。要裏付け）
4. **最小権限が先、承認は次。** OWASP は承認・ログ・レート制限は「被害を減らす」だけで、過剰な権限そのものは防がないとする
5. **承認の内容は、判断に必要な情報だけを見せる。** 承認が瞬時に全件通るようなら形骸化のサイン。承認率・所要時間を測る
6. 状態の永続化と、誰が承認したかの記録（監査ログ）が要る

## 3. 本プロジェクトの現状と比較
- 自前方式（Firestore に承認待ちを保存）は、LangGraph のチェックポイント方式と同じ考え方で、ADK 標準の弱点（永続セッション非対応）を避けられる。ツール名・引数・本人・24時間の期限・1回限り、に結びつけ済み（`hackathon_agent/governance/approvals.py`）
- 足りないもの: 「承認する人」を本人と別にする仕組み（ADK 標準も未定義）、承認画面、承認の対象となる実際の操作

## 4. 対象操作の候補と評価
| 候補 | リスク | 判定 |
|---|---|---|
| 奨学金データの検索・判定 | 読み取りのみ | 承認なし（現状どおり） |
| 本人用の通知・カレンダー登録 | 本人にしか影響せず、取り消せる | 承認なし（本人の「登録する」操作で足りる） |
| **共有データ（他の学生にも見える）への書き込み** | Webページに仕込まれた偽情報が他人に永続的に届く。取り消しにくい | **承認を必須にする** |
| 外部へのメール送信・応募 | 取り消せない | 作らない（拒否リスト） |

## 5. 推奨
- **対象操作: 共有の奨学金データへの書き込み**（設計済みの「奨学金データの共有」）。Web から読んだ情報が他の学生に残る唯一の経路なので、守る価値が最も大きく、承認の回数も少ない（疲れない）
- **承認者は、依頼した本人とは別の管理者**（職務分離）。学生が自分の依頼を承認できない
- 方式は既存の自前方式を維持。承認は「操作・引数・本人・期限・1回限り」に結びつける
- 承認画面（保留の一覧、承認／却下、理由）と、承認率・所要時間の表示を最小限で作る。デモでは「保留 → 管理者が承認 → 実行 → 監査ログ」を見せる
- 3段階（自動／承認／拒否）を明示する：読み取り・自分用 = 自動、共有書き込み = 承認、メール送信・応募 = 拒否
